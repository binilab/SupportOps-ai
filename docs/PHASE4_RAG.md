# Phase 4 — 정책 근거 답변과 보류

## 실행

Python 3.11 이상과 [로컬 Ollama](https://ollama.com/download)가 필요하다. API 키는 사용하지 않는다. Ollama 앱 또는 `ollama serve`로 서버를 실행한다. [Ollama Python SDK](https://github.com/ollama/ollama-python)의 구조화된 응답 호출을 먼저 단일 질문으로 확인하고, 같은 SDK 호출을 최종 경로에만 남겼다. 이 단계의 파이프라인은 검색 1회, 생성 1회, 인용 검증으로 끝나므로 LangChain을 추가해도 데이터 흐름이 단순해지지 않는다.

```bash
ollama pull gemma4:12b
python3 -m pip install -e '.[dev]'
python3 scripts/ask_policy.py '제주도는 배송비가 더 붙어?'
python3 scripts/validate_gold_dataset.py
python3 -m pytest -q
python3 scripts/evaluate_rag.py > reports/phase4_rag_local.json
python3 scripts/summarize_rag_review.py
```

Ollama 서버가 실행 중이어야 한다. 기본 모델은 `gemma4:12b`이며 로컬 모델을 바꿔 실험하려면 `SUPPORTOPS_RAG_MODEL` 환경 변수를 사용한다. 평가 수치는 보고서에 기록한 모델 digest에만 해당한다. `ollama` Python SDK 버전은 `0.6.3`으로 고정한다. [Ollama 구조화 출력 문서](https://docs.ollama.com/capabilities/structured-outputs)

## 입력 → 처리 → 출력

1. 기존 Phase 3 Hybrid 검색에서 상위 정책 3개를 고른다. 각 정책의 청크를 원본 경로와 ID를 보존하며 생성 문맥에 제공한다. 검색에서 가장 높은 청크를 먼저 배치한다.
2. 모델은 짧은 한국어 답변, 보류 여부, 사용한 청크 ID를 JSON으로 반환한다. 온도 0, 출력 상한 180 토큰, 내부 추론 출력 비활성화로 실행했다.
3. 코드가 청크 ID가 실제 제공한 근거에 있는지 확인하고 정책 ID·원본 파일 경로를 인용으로 반환한다. 존재하지 않는 ID나 빈 인용은 보류한다.
4. 주문 ID, 제삼자 개인 연락처, 조회가 필요한 개인 쿠폰 금액은 현재 가진 정책 데이터만으로 확인할 수 없어 모델 호출 전에 보류한다. 모델이 다른 질문에서 보류를 요청해도 표준 안내 문구만 반환한다.

이는 정책만으로 답할 수 있는 질문에 대한 RAG다. 주문/상품 데이터 조회, 쿠폰 발급 정보 조회, 실제 환불 적격성 결정, Tool Calling은 포함하지 않는다. 인용 ID의 존재 여부는 코드로 검증하지만 문장이 해당 근거에서 논리적으로 따라오는지는 자동 보장하지 않는다.

## 평가 방식

Phase 0부터 고정된 Gold 40개와 정책 8개/청크 35개를 사용했다. 정책만으로 답해야 하는 25개와 현 단계에서 보류해야 하는 15개로 나누었다. 후자에는 Tool이 필요한 11개가 포함된다. 두 집합의 기대 행동은 Gold의 `answerable`·`needs_tool` 필드로 사전에 결정했다.

- **답변 정확성:** 답해야 하는 25개에서 Gold의 필수 사실을 모두 전달했는지 사람이 답변별로 판정한다. 빠진 조건이나 잘못된 단정은 실패다.
- **근거 충실도:** 실제 답한 사례에서 모든 실질적 주장에 인용한 정책 청크의 근거가 있는지 사람이 판정한다.
- **인용 정확성:** 실제 답한 사례에서 인용한 청크가 답변의 실질적 주장을 뒷받침하는지 사람이 판정한다. 정책 ID precision/recall은 Gold ID와의 자동 대조값으로 따로 표시한다.
- **보류 정확성:** 보류가 기대되는 15개에서 실제 보류한 비율이다.

사람이 확인한 실패 ID는 `reports/phase4_review.json`에 응답 파일 SHA-256과 함께 기록한다. 재검토 시 원본 답변과 정책 청크를 대조할 수 있다. 수동 판정은 한 사람이 수행했으며 독립된 두 번째 평가자는 없다. 단일 로컬 실행의 응답은 온도 0이어도 환경에 따라 조금 달라질 수 있다.

## 결과와 한계

| 지표 | 최종 로컬 실행 |
|---|---:|
| 정책 질문 답변 여부 | 25/25 (100%) |
| 답변 정확성: Gold 필수 사실 전부 포함, 수동 검토 | 22/25 (88%) |
| 근거 충실도: 답한 사례 중 인용 청크로 뒷받침, 수동 검토 | 25/25 (100%) |
| 인용 정확성: 답한 사례 중 청크가 실질적 주장을 뒷받침, 수동 검토 | 25/25 (100%) |
| 정책 ID 인용 precision / recall, Gold 대조 | 0.980 / 0.960 |
| 보류 정확성 | 15/15 (100%) |
| 전체 질문당 시간 중앙값 / p95 | 24.218초 / 36.234초 |

로컬 모델 digest는 `4eb23ef187e2c5462566d6a1d3bbbc2f1346d0b4327cbb66d58fffbcc9b2b05c`다. Gold·정책 SHA-256은 Phase 1~3과 같다. latency는 모델 적재와 문서 임베딩 생성을 제외하고 검색·생성·검증을 포함한다. 15개 보류 사례 중 13개는 모델을 호출하지 않는 경로이므로, 전체 중앙값은 실제 생성 질문의 시간을 작게 보인다. 정책 답변 25개만 보면 중앙값은 26.393초였다. 모델 버전·하드웨어·서버 상태가 다르면 수치도 달라진다.

수동 검토에서 `eval_0038`은 교환 가능 여부의 동일 옵션 재고 조건을, `eval_0039`는 개별 쿠폰 조건이 없을 때 일반 정책을 따르는 규칙을, `eval_0040`은 개별 조건의 우선순위를 답변에서 빠뜨렸다. `eval_0010`과 `eval_0040`은 답변의 핵심을 뒷받침하는 인용은 있으나 Gold가 요구한 정책 ID를 모두 인용하지 않아 자동 정책 ID recall도 낮아졌다. 수동 100% 값은 이 25개 출력에 대한 판정이며, 다른 질문에서 환각이나 잘못된 인용이 없음을 뜻하지 않는다.

초기 결과를 보고 프롬프트와 보류 규칙을 수정했으므로 이 Gold는 이 단계에서 개발 평가셋으로도 사용됐다. 88%를 미지의 질문에 대한 일반화 성능으로 해석할 수 없다. 이 모델의 20초대 응답 시간은 현재 상담원 보조 작업에 그대로 적용하기에는 느리다. Phase 4는 평가 가능한 로컬 RAG의 동작과 실패 경계를 확인한 단계다. 응답 속도 최적화나 실제 주문 데이터 결합은 이번 범위에 넣지 않았다.
