# ENGINEERING GUIDE — 개발 운영 가이드

여러 개의 작은 문서로 흩어질 수 있는 개발 규칙을 이 파일 하나에 모은다.

## 1. 역할 분담
- **사용자:** 프로젝트 범위와 최종 의사결정의 책임자. 결과를 확인하고 Trade-off를 이해한다.
- **ChatGPT 프로젝트:** WHY/WHAT 담당. 다음 작업 결정, 개념 학습, 실험 설계, 지표 해석, 면접 대비를 돕는다. 저장소 상태가 필요하면 연결된 GitHub의 `PROGRESS.md`를 우선 확인하고, 접근할 수 없으면 사용자에게 최신 `PROGRESS.md` 또는 Codex 작업 요약만 요청한다.
- **Codex:** HOW 담당. 저장소 확인, 코드 수정, 테스트, 디버깅, 제한된 범위의 리팩터링을 수행한다.

## 2. 표준 작업 사이클
1. `PROGRESS.md`를 읽는다.
2. 작업 1개와 측정 가능한 완료 조건을 정의한다.
3. 큰 수정 전에는 먼저 계획을 세운다.
4. 해당 작업만 구현한다.
5. 테스트/평가를 실행한다.
6. Git diff와 핵심 경로를 확인한다.
7. 실패/경계 사례를 시도한다.
8. 결과를 해석한다. “실행된다”만으로 완료 처리하지 않는다.
9. 진행 상태 문서를 갱신한다.
10. 의미 있는 작업 단위로 커밋한다.
11. ChatGPT 프로젝트가 GitHub에서 최신 상태를 볼 수 있도록 의미 있는 마일스톤이 끝나면 원격 저장소에도 반영한다. Codex가 push 권한을 사용할 수 없으면 사용자가 실행할 정확한 명령을 안내한다.

## 3. 사용자가 반드시 이해해야 할 것
모든 코드를 한 줄씩 설명할 필요는 없다. 대신 핵심 코드 경로에 대해서는 다음을 설명할 수 있어야 한다.
- 입력 / 출력
- 중요한 타입과 벡터/행렬 shape
- 데이터/상태 흐름
- 외부 라이브러리가 대신하는 역할
- 예상 가능한 실패 사례
- 정상 동작을 검증하는 방법
- 이 설계를 선택한 이유

보일러플레이트를 줄 단위로 외우는 데 시간을 쓰지 않는다.

## 4. 디버깅 규칙
문제가 발생하면 다음 순서를 따른다.
1. 오류 메시지를 읽는다.
2. 실패 위치를 찾는다.
3. 실제 입력값/타입/shape/상태를 확인한다.
4. 예상값과 실제값을 비교한다.
5. 원인 가설을 세운다.
6. 가장 작은 수정으로 고친다.
7. 필요하면 회귀 테스트를 추가한다.

## 5. 핵심 데이터 설계
한 회사 세계의 정책과 주문 정보가 서로 일관되도록 핵심 데이터는 합성으로 만든다.

- `data/raw/policies/`: 검색 대상 정책 지식
- `data/raw/structured/`: 상품/주문 구조화 데이터. 이후 PostgreSQL에 적재
- `data/eval/gold_dataset.jsonl`: 고정 Gold 평가셋
- `data/external/`: 출처가 기록된 선택적 외부 데이터

안정적인 ID 규칙:
- 정책: `policy_*`
- 상품: `P-####`
- 주문: `ORD-####`
- 평가 예시: `eval_####`

외부 데이터를 사용하면 `data/external/SOURCE_MANIFEST.md`에 다음을 기록한다.
- 출처
- 라이선스/이용조건
- 확인 날짜
- 사용한 범위
- 가공 방식
- 사용 목적

외부 데이터가 MoaShop의 비즈니스 규칙을 조용히 바꾸게 해서는 안 된다.

## 6. 평가 설계
Gold 평가셋은 최적화 전에 만든다. 성능 수치를 높이기 위해 어려운 질문을 삭제하지 않는다.

중요 평가 유형:
- 정책 키워드가 직접 들어간 질문
- Paraphrase 질문
- 정확한 식별자/숫자 질문
- 여러 조건이 함께 들어간 질문
- Tool 호출이 필요한 질문
- 정책 + Tool이 함께 필요한 질문
- 답변 불가능/범위 밖 질문
- 모호하거나 노이즈가 있거나 공격적인 표현

검색 최소 평가 지표:
- Recall@1/3/5
- MRR
- latency

RAG 최소 평가 지표:
- 답변 정확성
- 근거 충실도
- Citation 정확성
- Abstention 정확성

Tool/Agent 최소 평가 지표:
- Tool 선택 정확도
- 인자 정확도
- 최종 작업 성공률

개선 결과를 기록할 때는 최소한 다음을 함께 남긴다.
- 평가 데이터 버전/개수
- 설정값
- 품질 지표
- latency
- 어떤 유형에서 실패했는지

## 7. 코드 리뷰 체크리스트
다음을 확인한다.
- 현재 범위 안의 변경인가?
- 불필요한 의존성/추상화를 추가하지 않았는가?
- 핵심 데이터 흐름을 설명할 수 있는가?
- 가정이 명시되어 있는가?
- 확정적 규칙이 확정적 코드로 구현되어 있는가?
- 오류가 조용히 무시되지 않고 드러나는가?
- 정상 사례뿐 아니라 실패/경계 사례도 테스트했는가?
- AI 동작을 눈으로만 보고 판단하지 않고 평가했는가?
- Citation이 실제 검색 근거와 연결되는가?
- Tool 인자가 검증되는가?
- “더 좋아졌다”라고 말할 수 있는 측정 근거가 있는가?

## 8. 외부 도구/서비스를 자동으로 사용할 수 없을 때
외부 연동을 자동으로 끝낼 수 없다면 다음 규칙을 따른다.
- 무엇이 부족한지 정확히 말한다. 예: API 키, Docker Desktop, PostgreSQL 확장, 계정 로그인, 클라우드 권한
- 사용자가 해야 할 정확한 설정 절차를 알려준다.
- 자격증명을 지어내거나 성공한 척하지 않는다.
- 현재 단계의 학습/평가 목적을 유지할 수 있을 때만 Mock을 사용하고, Mock임을 명확히 표시한다.
