# SupportOps AI — 면접 질문과 답변

이 문서는 현재 구현과 고정 개발 평가 결과를 설명하기 위한 메모다. 수치는 [원본 보고서](../reports)와 [README](../README.md)에 연결돼 있다.

## 1. 어떤 문제를 해결하나?

상담원이 정책 문서와 주문 상태를 따로 찾아야 하는 부담을 줄인다. 정책 질문은 출처를 붙여 답하고, 주문 질문은 읽기 전용 조회와 결정적 규칙으로 판단한다. 모르는 주문 상태나 개별 조건은 확정하지 않는다.

## 2. 왜 합성 데이터와 고정 Gold를 썼나?

정책·주문·상품이 서로 일치하는 작은 세계를 만들면서 실제 개인정보를 다루지 않기 위해서다. 검색 방법을 바꾸기 전에 같은 Gold와 정책 Corpus를 고정해 비교했다. 다만 구현 중 Gold를 다시 사용했으므로 별도 held-out 성능은 아직 없다.

## 3. Recall@K와 MRR은 무엇을 측정하나?

필수 정책 ID가 상위 K개에 있는지와 첫 관련 정책이 얼마나 앞에 있는지를 측정한다. 40개 중 정책 ID가 있는 37개만 검색 평가에 포함했다. 이 지표는 청크 적합성, 답변 정확성, 인용 충실도를 직접 측정하지 않는다.

## 4. 왜 BM25와 Dense를 RRF로 결합했나?

BM25는 매우 빠르지만 한국어 표현 차이와 오타에 약했고, Dense는 상위 1개 순위가 나아졌지만 상위 5개에서 일부 필수 정책을 놓쳤다. 원점수 척도가 달라 정책 ID 순위를 RRF 상수 60으로 합쳤다. 같은 Gold에서 Hybrid Recall@3은 0.9324로 Dense 0.8378보다 높았고, 검색 중앙 시간은 약 0.528ms 길었다. `eval_0033`은 여전히 실패한다.

## 5. pgvector를 썼는데 API는 왜 로컬 Dense인가?

Phase 2에서 pgvector에 정책 벡터 35개를 실제 저장·조회하고 로컬 Dense와 같은 검색 지표를 확인했다. 현재 작은 Corpus의 API는 Phase 3에서 평가한 로컬 Hybrid 경로를 그대로 사용한다. pgvector 실험 결과를 서비스 사용으로 표현하지 않으며, API의 PostgreSQL은 주문·상품 조회에 쓰인다.

## 6. 답변의 환각과 잘못된 인용을 어떻게 제한하나?

정책 생성에는 검색된 청크와 ID를 제공하고, 반환한 인용 ID가 제공된 청크에 있을 때만 답변한다. 근거가 없거나 잘못된 ID면 보류한다. 이는 **인용 존재 검증**이지 모든 문장의 논리적 충실도 보증이 아니다. 수동 검토에서 필수 조건을 빠뜨린 RAG 답변 3개가 남았다.

## 7. 환불·취소 판단을 왜 Python 규칙에 뒀나?

신청 기간, 주문 상태, 재판매 어려운 상태, 주문제작·위생·디지털 제한은 명시적 조건으로 테스트할 수 있다. `used=true`만으로 환불 불가를 추정하지 않고, 고객의 하자 주장만으로 회사 귀책을 확정하지 않는다. 모델은 주문 질문의 첫 Tool과 의도를 제안하고, 실제 적격성 분기는 코드가 수행한다.

## 8. 모델이 잘못된 Tool 인자를 주면?

질문에 있는 주문 ID와 모델이 제안한 ID, Tool 이름, 의도를 확인한다. 다르면 조회를 실행하지 않고 보류한다. 존재하지 않는 주문은 `get_order` 후 멈추며 다른 주문을 추측하지 않는다. 후속 상품 조회 순서도 모델이 자유롭게 결정하지 않는다.

## 9. 왜 LangChain과 LangGraph를 도입하지 않았나?

정책 흐름은 검색 1회, 생성 1회, 인용 검증으로 충분했고, 주문 후속 Tool 순서는 데이터 의존성이 고정돼 있다. 이 범위에서 프레임워크가 흐름을 단순화한다는 근거가 없었다. 상태 저장·재개나 복잡한 승인 분기가 생기면 그때 다시 평가한다.

## 10. 11/11 Workflow 성공을 어떻게 설명해야 하나?

고정 Gold의 Tool 필요 질문 11개에서 첫 Tool, 인자, 전체 순서, 판정, 보류가 기대값과 맞았다는 뜻이다. 이 사례는 개발 중 사용됐고 한 사람이 답변 필수 사실을 검토했다. 실제 운영 질문에 대한 100% 성공률이라고 주장하지 않는다.

## 11. 지연 시간과 첫 실행 문제는?

로컬 정책 RAG는 답변 대상의 중앙 시간이 26.393초였고, 첫 Compose 정책 요청은 모델 다운로드까지 약 92초였다. 반면 주문 Workflow는 고정 Gold에서 중앙 0.759초였다. 측정 환경이 달라 직접적인 서비스 SLA로 사용하지 않는다. 배포 전에 held-out 질문과 장시간 운영 부하를 따로 측정해야 한다.

## 12. CI가 검증하는 것과 못 하는 것은?

GitHub Actions는 Gold 구조, 결정적 규칙, API 요청·오류 경계, 실제 PostgreSQL/pgvector 통합 경로를 테스트한다. 로컬 Ollama를 설치하지 않으므로 생성 답변 품질은 CI에서 재평가하지 않는다. 그 결과는 모델 digest와 수동 검토가 붙은 별도 실험 보고서로 관리한다.
