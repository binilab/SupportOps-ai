# 설계 결정

## 범위

| 포함 | 제외 |
|---|---|
| 정책 8종: 배송, 주문 취소, 교환, 환불, 쿠폰, 포인트, 회원, 상품별 제한 | 실제 결제·환불·취소 실행 |
| 합성 주문 10건, 상품 10건 | 실제 고객 개인정보 |
| 정책 질문 답변, 주문 질문의 환불·취소 가능 여부 판단, 배송 상태 안내 | 인증, 클라우드 배포 |
| 근거가 부족한 질문 보류 | 음성, 파인튜닝, 멀티 에이전트 |

사용자는 고객센터 상담원이다. 상담원이 고객에게 답하기 전에 정책 문서와 주문 정보를 따로 찾아보는 부담을 줄이고, 답변의 근거를 추적할 수 있게 하는 것이 목표다.

## 1. 하나의 가상 쇼핑몰(MoaShop)로 데이터를 직접 설계

공개 Q&A 데이터셋으로는 정책·주문·상품·평가 정답이 서로 맞물리는 상황을 만들기 어렵다. 그래서 가상의 패션·생활용품 쇼핑몰을 정하고 정책 문서, 주문·상품 CSV, 평가셋을 같은 규칙으로 만들었다. 예를 들어 주문 환불 질문의 정답은 주문 CSV의 배송 완료일·사용 여부와 환불 정책의 기간·예외 조항이 실제로 맞물려야 정해진다.

## 2. 평가셋을 먼저 만들고 고정

검색 방식을 고르기 전에 40문항 평가셋을 만들고 버전 관리했다. 결과를 본 뒤 잘 맞는 질문만 남기는 일을 막고, 방법을 바꿀 때마다 같은 기준으로 비교하기 위해서다. 성능이 낮게 나와도 평가셋이나 정책 문구는 고치지 않았다.

정책 경계 조건도 이때 확정했다.
- 일반 상품은 포장 개봉만으로 단순 변심 환불·교환을 거절하지 않는다. 착용·세탁·오염·스크래치로 재판매가 어려울 때 거절한다.
- 하자·오배송은 고객 주장만으로 확정하지 않고 사진이나 상담으로 확인한다. 회사 귀책이 확인되면 배송비는 회사가 부담한다.
- 상품·쿠폰별 개별 조건은 일반 정책보다 우선하고, 개별 조건이 없으면 일반 정책을 따른다.

## 3. 환불·취소 판단은 LLM이 아니라 코드로

환불 기간, 상품 종류별 제한처럼 조건으로 표현할 수 있는 판단은 `eligibility.py`의 규칙으로 구현했다.

- 같은 주문·같은 날짜에는 항상 같은 결과가 나온다.
- 7일째와 8일째 같은 경계값을 테스트로 고정할 수 있다.
- 답변 문구도 판단 결과에 따라 코드에서 고르므로 판단과 다른 답변이 나갈 수 없다.

LLM은 오타가 섞인 자연어에서 주문 ID와 요청 종류(환불/취소/배송)를 뽑는 데만 쓴다.

## 4. LLM 출력은 검증한 뒤에만 사용

- **라우터:** 모델이 제안한 주문 ID가 질문의 주문 ID와 다르면 조회하지 않는다. 다른 고객의 주문을 잘못 조회하는 일을 막기 위해서다.
- **답변 모델:** 넘겨준 근거에 없는 청크 ID를 인용하면 답변 전체를 보류한다. JSON 형식이 깨져도 보류한다.
- **범위 밖 질문:** 주문 정보, 다른 사람의 연락처, 개인 쿠폰 금액처럼 정책 문서로 알 수 없는 질문은 모델을 부르기 전에 규칙으로 보류한다.

## 5. 검색은 BM25 + 임베딩을 RRF로 결합

BM25는 정확한 키워드에 강하고, 임베딩은 바꿔 말한 질문에 강했다. 두 점수는 범위가 달라 그대로 더할 수 없어서 순위만 쓰는 RRF로 합쳤다. 평가셋에서 Recall@1/3/5와 MRR이 모두 가장 높았고, 추가 검색 시간은 약 0.5 ms였다.

재순위화 모델(CrossEncoder)은 이번 범위에서는 도입하지 않았다. 남은 검색 실패(오타 질문)를 줄이는 다음 실험 후보다.

정책 청크가 35개뿐이라 서비스는 메모리 검색을 쓴다. pgvector 저장·검색은 구현해서 메모리 검색과 결과가 같은지 확인했고, DB 통합 테스트로 유지한다.

## 6. LangChain·LangGraph를 쓰지 않음

정책 답변은 검색 1회 → 생성 1회 → 인용 검증으로 끝나고, 주문 처리는 도구 순서가 데이터 의존성으로 정해져 있다. 상태 저장이나 재개, 승인 분기가 필요 없어서 프레임워크를 넣어도 코드가 단순해지지 않았다. Ollama Python SDK의 structured output과 tool calling을 직접 썼다.

## 7. 로컬 LLM (Ollama)

API 키 없이 실제 생성 결과를 평가셋과 비교할 수 있도록 로컬 모델을 썼다.

| 용도 | 모델 | 측정 결과 |
|---|---|---|
| 주문 질문 라우팅 | `qwen2.5:3b` | 도구 호출·인자 11/11, 응답 중앙값 0.76초 |
| 정책 답변 생성 | `gemma4:12b` | 필수 사실 포함 22/25, 응답 중앙값 26.4초 |

라우터는 도구 호출과 요청 종류 분류만 하면 돼서 작은 모델을 썼다. 정책 답변은 질문당 20초대가 걸려 실제 상담 보조로는 느리다. 모델은 환경 변수(`SUPPORTOPS_AGENT_MODEL`, `SUPPORTOPS_RAG_MODEL`)로 바꿀 수 있고, 바꾸면 같은 평가셋으로 다시 측정해야 한다.

## 8. 서비스 구성

- API는 읽기 전용이다. 주문·상품 데이터는 `scripts/init_database.py`로 따로 적재하고, 요청 처리 중에는 데이터를 바꾸지 않는다.
- 적재를 다시 실행해도 중복 삽입하지 않고, DB 값이 CSV와 다르면 덮어쓰지 않고 오류를 낸다.
- DB·모델 장애는 503, 입력 오류는 422, 그 밖의 오류는 500으로 나누고, 내부 예외 메시지는 응답에 넣지 않는다.
- 요청마다 요청 ID, 결과 코드, 지연 시간, 토큰 수를 JSON 한 줄로 로그에 남긴다. 질문 원문과 주문 상세는 로그에 남기지 않는다.
- Docker Compose는 DB 준비 → 데이터 적재 → API 시작 순서로 띄운다. Ollama는 컨테이너가 아니라 호스트에서 실행해 모델을 다시 내려받지 않게 했다.
