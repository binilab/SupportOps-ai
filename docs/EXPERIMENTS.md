# 실험 기록

검색 → 정책 답변(RAG) → 주문 처리 순서로 기능을 붙이면서, 매 단계를 같은 평가셋으로 측정한 기록이다.
원본 수치는 모두 `reports/`의 JSON에 있고, 이 문서는 그 요약과 해석이다.

## 1. 평가셋

`data/eval/gold_dataset.jsonl`에 40문항을 만들어 두고 끝까지 바꾸지 않았다. 문항마다 다음을 미리 정했다.

- `expected_policy_ids`: 답하려면 찾아야 하는 정책
- `expected_facts`: 답변에 반드시 들어가야 하는 사실
- `answerable`, `needs_tool`, `expected_tools`: 답할 수 있는 질문인지, 주문 조회가 필요한지, 어떤 순서로 도구를 써야 하는지

유형은 키워드가 그대로 들어간 질문, 같은 뜻을 다르게 표현한 질문, 주문 ID·숫자가 들어간 질문, 조건이 여러 개 겹친 질문, 오타가 있는 질문, 정책 밖 질문으로 나눴다.
`python3 scripts/validate_gold_dataset.py`는 필수 필드, 중복 ID, 존재하지 않는 정책 ID, 도구 관련 필드의 일관성을 검사한다.

평가셋을 개발 중에도 보면서 프롬프트와 규칙을 고쳤기 때문에, 아래 수치는 일반화 성능이 아니라 개발 평가 결과로 봐야 한다.

## 2. 정책 검색

### 조건

- 정책 문서 8개를 `##` 소제목 단위로 나눠 청크 35개를 만들었다. 청크 ID는 `정책ID::번호` 형식이다.
- 정답 정책이 있는 37문항으로 평가했다 (정책 밖 질문 3개 제외).
- 지표는 정책 ID 기준이다. 같은 정책의 청크가 여러 개 나와도 정책 하나로 센다.
  - Recall@k: 정답 정책 중 상위 k개 안에 들어온 비율의 평균
  - MRR: 첫 정답 정책 순위의 역수 평균
- 검색 시간은 모델 로딩과 문서 임베딩 생성을 뺀 `search()` 호출 시간이다. 이 컴퓨터에서 한 번 실행한 값이라 참고용이다.

### 방법

| 방법 | 내용 |
|---|---|
| BM25 | 소문자화 후 `[가-힣A-Za-z0-9]+`로 토큰화, `rank-bm25`의 BM25Okapi. 형태소 분석은 하지 않았다. |
| 임베딩 | `paraphrase-multilingual-MiniLM-L12-v2` (revision 고정, CPU, 384차원 정규화 벡터), 코사인 유사도 |
| 임베딩 + pgvector | 같은 벡터를 PostgreSQL pgvector에 저장하고 `<=>` 연산자로 정확 검색 |
| 하이브리드 | BM25와 임베딩의 정책 순위를 RRF로 결합. 정책마다 `1 / (60 + 순위)`를 더한다. |

RRF를 쓴 이유는 BM25 점수와 코사인 유사도는 범위가 달라 그대로 더할 수 없기 때문이다. 상수 60은 원 논문의 값을 그대로 썼고 평가셋에 맞춰 조정하지 않았다.

### 결과

| 방법 | Recall@1 | Recall@3 | Recall@5 | MRR | 검색 시간 중앙값 | 상위 5개 누락 |
|---|---:|---:|---:|---:|---:|---:|
| [BM25](../reports/phase1_bm25_baseline.json) | 0.6081 | 0.8378 | 0.9459 | 0.7883 | 0.045 ms | 2 |
| [임베딩](../reports/phase2_dense_local.json) | 0.7297 | 0.8378 | 0.9189 | 0.8905 | 5.680 ms | 5 |
| [임베딩 + pgvector](../reports/phase2_dense_pgvector.json) | 0.7297 | 0.8378 | 0.9189 | 0.8905 | 7.071 ms | 5 |
| **[하이브리드](../reports/phase3_hybrid_rrf.json)** | **0.7432** | **0.9324** | **0.9730** | **0.9009** | 6.208 ms | **1** |

- BM25는 상위 5개 안에 정답을 넣는 데는 강했지만 1위 정확도가 낮았다. 임베딩은 반대로 1위 정확도와 MRR이 높았지만 여러 정책이 필요한 질문에서 두 번째 정책을 놓쳤다.
- 하이브리드는 두 방식의 장점을 합쳐 모든 지표가 가장 높았다. 임베딩보다 Recall@3이 0.095 올랐고, 검색 시간은 약 0.5 ms 늘었다. 서비스에는 하이브리드를 쓴다.
- pgvector는 메모리 검색과 모든 지표·실패 목록이 같았다. 정책 청크가 35개뿐이라 근사 인덱스(HNSW 등) 없이 정확 검색을 썼다.

### 실패 사례

- `eval_0018` "ORD-9999 환불돼?": BM25에서 `환불돼`와 `환불`이 다른 토큰이라 매칭되지 않았다. 하이브리드에서는 임베딩 쪽이 찾아 해결됐다.
- `eval_0010`, `0013`, `0016`, `0040`: 임베딩에서 주문제작·위생·개별 조건 질문의 두 번째 정책(`policy_product_restrictions_v1`)이 밀렸다. 하이브리드에서 해결됐다.
- `eval_0033` "야, ORD-1008 취쏘 되냐??": 모든 방법에서 취소 정책을 찾지 못한 남은 실패다. 다만 주문 ID가 있는 질문이라 서비스에서는 검색이 아니라 주문 처리 경로로 가고, 그 경로에서는 정상 처리됐다 (4절).

## 3. 정책 답변 (RAG)

### 방법

- 하이브리드 검색으로 상위 정책 3개를 고르고, 각 정책의 청크를 모두 근거로 넘긴다. 예외 조항이 다른 섹션에 있는 경우가 많아 청크 하나만 넘기면 조건을 빠뜨리기 쉬웠다.
- 로컬 Ollama `gemma4:12b`, temperature 0, 출력 180토큰. JSON 형식(답변, 보류 여부, 사용한 청크 ID)을 강제한다.
- 모델이 인용한 ID가 넘겨준 근거에 없으면 답변 전체를 보류한다.
- 주문 ID, 다른 사람의 개인 연락처, 개인 쿠폰 금액처럼 정책 문서로 알 수 없는 질문은 모델을 부르기 전에 보류한다.

### 결과

정책만으로 답해야 하는 25문항과 보류해야 하는 15문항(주문 조회가 필요한 11문항 포함)으로 나눠 평가했다.

| 지표 | 결과 |
|---|---:|
| 답변해야 할 질문에 답변 | 25/25 |
| 필수 사실을 모두 포함 (수동 검토) | 22/25 |
| 답변 내용이 인용한 근거로 뒷받침됨 (수동 검토) | 25/25 |
| 인용한 청크가 실제 주장을 뒷받침 (수동 검토) | 25/25 |
| 정책 ID 인용 precision / recall (자동 대조) | 0.980 / 0.960 |
| 보류해야 할 질문을 보류 | 15/15 |
| 답변한 질문의 응답 시간 중앙값 | 26.4초 |

[원본 출력](../reports/phase4_rag_local.json) · [수동 검토 기록](../reports/phase4_review.json)

### 실패 사례

- `eval_0038`: 교환 가능 여부에서 "같은 옵션 재고가 있어야 한다"는 조건을 빠뜨렸다.
- `eval_0039`: 개별 쿠폰 조건이 없으면 일반 정책을 따른다는 규칙을 빠뜨렸다.
- `eval_0040`: 개별 조건이 일반 정책보다 우선한다는 점을 빠뜨렸다.

세 경우 모두 인용 자체는 맞았다. 인용 ID 검증은 "근거가 실제로 존재하는가"만 보장하고, 답변이 근거의 모든 조건을 담았는지는 보장하지 못한다는 한계가 여기서 드러났다.

## 4. 주문 처리 (도구 호출 + 규칙)

### 방법

```text
질문 → 라우터 LLM이 get_order(order_id, intent) 호출을 제안
     → 주문 ID가 질문과 같은지, intent가 refund/cancel/shipping인지 검증
     → 주문 조회 → (필요하면) 상품 조회 → 환불/취소 규칙 판단
     → 판단 결과에 맞는 답변·인용 정책 (코드에서 선택)
```

- 라우터는 로컬 `qwen2.5:3b`의 tool calling을 쓴다. 모델은 첫 도구와 요청 종류만 고르고, 이후 순서는 코드가 정한다.
- 환불 규칙: 신청 기간(배송 완료 다음 날부터 7일), 주문 상태, 주문제작·위생·디지털 상품 제한, 구성품 보존, 재판매가 어려운 손상.
- 사용 이력(`used=true`)만으로 재판매 불가라고 단정하지 않고 확인 필요로 둔다.
- 고객의 하자·오배송 주장은 회사 귀책으로 확정하지 않고 확인 필요로 둔다.

### 결과

주문 조회가 필요한 11문항으로 평가했다. 없는 주문(`ORD-9999`), 송장 정보가 없는 배송 위치 질문, 오타가 있는 취소 질문이 포함된다. 기준일은 `2026-10-05`로 고정했다.

| 지표 | 결과 |
|---|---:|
| 첫 도구(`get_order`) 선택 | 11/11 |
| 주문 ID·요청 종류 인자 | 11/11 |
| 전체 도구 순서 | 11/11 |
| 판정 결과 | 11/11 |
| 보류 여부 | 11/11 |
| 필수 사실 포함 (수동 검토) | 11/11 |
| 응답 시간 중앙값 / p95 | 0.76초 / 2.90초 |

[원본 출력](../reports/phase5_agent_local.json) · [수동 검토 기록](../reports/phase5_review.json)

전체 도구 순서는 모델이 혼자 정한 것이 아니라 코드가 정하므로, 이 수치는 "라우터 제안 + 코드 검증"을 합친 흐름의 정확도다.

## 5. 재현

```bash
python3 -m pip install -e '.[dev]'
python3 scripts/evaluate_bm25.py > reports/phase1_bm25_baseline.json
python3 scripts/evaluate_dense.py --backend local > reports/phase2_dense_local.json
python3 scripts/evaluate_hybrid.py > reports/phase3_hybrid_rrf.json

# Ollama 필요
python3 scripts/evaluate_rag.py > reports/phase4_rag_local.json
python3 scripts/evaluate_agent.py > reports/phase5_agent_local.json
```

pgvector 평가는 PostgreSQL이 필요하다 ([실행·운영 가이드](OPERATIONS.md) 참고).

```bash
export SUPPORTOPS_DATABASE_URL='postgresql://USER:PASSWORD@127.0.0.1:5432/supportops'
python3 scripts/evaluate_dense.py --backend pgvector > reports/phase2_dense_pgvector.json
```

보고서에는 평가셋·정책 파일의 SHA-256, 임베딩 모델 revision, Ollama 모델 digest를 함께 기록해서 어떤 조건에서 나온 수치인지 추적할 수 있다. LLM 답변은 temperature 0이어도 환경에 따라 문구가 조금 달라질 수 있다.
